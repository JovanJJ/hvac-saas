# Real confirmation email from local development

Supabase Auth sends confirmation/recovery messages. The development Inbucket service captures messages locally; it does not deliver to Gmail or another internet mailbox. Receiving at Gmail and sending through Gmail are separate choices: any working SMTP sender can deliver a confirmation to a Gmail recipient. No VPS is required to send mail from local development, but the confirmation URL must be reachable in the browser that opens it.

## Configure a sender

1. Choose a real SMTP provider/account. Add `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_ADMIN_EMAIL` and optionally `SMTP_SENDER_NAME` to the **existing Supabase project's private `.env`**, not the application's public/browser configuration. See [smtp.env.example](smtp.env.example) for a Gmail sender example. The sender address must be allowed by the provider.
2. Gmail sending requires an eligible Google account with 2-Step Verification and an App Password; do not use the normal account password. See [Google App Passwords](https://support.google.com/mail/answer/185833?hl=en). For another provider use its actual SMTP credentials. Do not send passwords in chat or commit them.
3. In this app's private `.env`, set `APP_URL` to the actual app origin. For development on the same computer this can remain `http://localhost:3000`.
4. Run `npm run mail:external:check`. It validates settings and Compose without restarting a service or sending a message. Success here does not establish SMTP connectivity, authentication or inbox delivery.
5. Run `npm run mail:external` to recreate only the existing Auth service with external SMTP and required email confirmation. The script discovers the existing Compose project, preserves unrelated overrides, replaces the known local-mail override and never resets the database or prints resolved credentials. It removes the development-only `LOCAL_AUTH_INBOX_URL` app setting. Restart Next.js if its development inbox link remains visible.
6. Register your own account through `/sign-up`, open the actual received confirmation and verify sign-in. Then exercise `/forgot-password`. These user-triggered actions send real messages; the configuration command itself sends no test email. Check spam if appropriate. Provider responses and credentials must not be copied into public logs.

The Auth override uses the application's origin for Site URL and exact callback/confirmation/recovery redirects. Existing email templates, verification routes and confirmation policy remain in use. Current signup uses the PKCE callback flow: open the link in the original registration browser. A localhost link opened in Gmail on a different phone/computer refers to that device, not the development host; use the previously documented USB port forwarding or a reachable trusted HTTPS address when testing on Android. Public URL changes also need corresponding Supabase public/API origins; the SMTP command does not provision a domain or tunnel.

`npm run mail:start` deliberately switches back to local capture for fictional automated tests, removing the external-mail override from its Compose invocation. Do not run it when the intent is real inbox delivery. Separate development/staging instances should have their own SMTP configuration and data. General self-hosted SMTP configuration is described in [Supabase Auth configuration](https://supabase.com/docs/guides/self-hosting/auth/config).

## Verification — 23 November 2026

Inspected the running Auth configuration without displaying credentials: it uses local capture on port 2500, no SMTP username/password and confirmation enabled. `mail:external:check` correctly stopped because the existing source SMTP host is local/placeholder. No Auth service was recreated and no email was sent.

Passed TypeScript, lint, 15 unit files and diff whitespace checks. A read-only Docker Compose comparison using fictional SMTP values verified that the external override changes only Auth, preserves literal credential handling and leaves confirmation required. After the sender settings were corrected, `mail:external:check` and `mail:external` succeeded. Only Auth was recreated; it reports healthy and its gateway health endpoint returns HTTP 200. External SMTP uses port 587 with required email confirmation. A separate TLS-protected SMTP login succeeded without sending a message.
