# HVAC field service app — development guide

The first working journey begins with a technician opening a visit on a phone. It ends when the office can tell the customer what happened to each AC system, what needs attention and who will follow up, using the technician's original entries.

**Start with the frontend.** Build a clickable, phone-first version of one four-system visit with fictional data. Show it to a technician and the person who prepares their reports. **For production, build sign-in and workspace isolation next.** Then connect the tested screens to real records. This order lets the field and office teams correct the form while changes are inexpensive, and it gives you a usable visit as soon as the data layer is in place.

This is an implementation companion for the developer and coding agents. The routes below are proposed Next.js App Router URLs. Dynamic segments such as `[visitId]` are record identifiers. A screen or button becomes production-ready in the milestone indicated. User-facing copy and PDFs use Serbian Latin. Code, tickets and project documents use English.

## 1. Build order and completion gates

Implement one row at a time. Within a production row, ship a small path from screen to server to stored data and back to the screen. Give the next agent the last passing scenario and the first unfinished ticket.

| Milestone | Work in dependency order | What Jovan can do before moving on |
| --- | --- | --- |
| **M0. Validate the field journey** | Obtain anonymized examples and time one job. Build Today → visit → system form → submission summary → office review → customer preview with an in-memory fixture. Let the technician and office try it separately. Record where they hesitate and which information they look for on paper. | On a narrow phone, record two serviced systems, one requiring repair, and one inaccessible. The office can tell exactly what it must do next. Agree on field names and the sample report with pilot prospects. |

| **M2. Complete one real visit online** | (1) Create a customer, site and systems manually. (2) Schedule a visit, select systems and assign a technician. (3) Open Today and save per-system outcomes, readings, parts and required follow-ups. (4) Submit, review, request a correction or open the customer preview. Configure HTTPS, public auth links, private service networking, persistent volumes, monitoring and backups. ## 5. Rules that affect multiple pages

- **Access and roles.** Owner and coordinator manage operational pages and issuance. Technicians work assigned visits and see the specific equipment history needed there. A guest can access only the revision identified by their link. Denied deep links and private downloads must reveal no other customer's details.
- **Export permission.** SPEC assigns the core CSV export to the owner. The coordinator row in DATABASE also mentions export. Implement owner-only for the full organization export in the pilot, test denial for coordinators, and align the two source documents when this decision is confirmed.
- **Visit status.** Use `scheduled → in_progress → submitted → issued`. Owner/coordinator can return a submitted visit to in-progress with a reason before issue, or cancel a scheduled/in-progress visit with a reason. Corrections after issuance create a new revision. Show rendering and sharing readiness separately from the visit status.
- **Outcomes and counts.** Start each visit item at `pending`. `serviced` and `repair_needed` count as inspected. `no_access` requires a reason and next action. Maintain the original planned set when an existing site system is added in the field. Show additional systems separately and include all inspected items in the inspected total. Include the planned/added distinction in the M2 schema and preview acceptance check.
- **Screen states.** For each data screen implement loading, empty, loaded, validation failure and recoverable server failure. Distinguish a denied/missing record from an empty list. Show actionable sync states on field screens and keep entered values after errors. Use keyboard operation, visible labels, large touch targets and text as well as color for statuses.
- **Pilot scope.** Manual enrollment and billing cover the pilot. Leave online checkout, tax invoices, inventory, regulatory certificates, a customer portal and enterprise dashboards for later decisions. The MVP's customer entry is the revision link.
