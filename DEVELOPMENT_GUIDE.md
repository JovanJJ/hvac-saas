# HVAC field service app — development guide

The first working journey begins with a technician opening a visit on a phone. It ends when the office can tell the customer what happened to each AC system, what needs attention and who will follow up, using the technician's original entries.

**Start with the frontend.** Build a clickable, phone-first version of one four-system visit with fictional data. Show it to a technician and the person who prepares their reports. **For production, build sign-in and workspace isolation next.** Then connect the tested screens to real records. This order lets the field and office teams correct the form while changes are inexpensive, and it gives you a usable visit as soon as the data layer is in place.

This is an implementation companion for the developer and coding agents. The routes below are proposed Next.js App Router URLs. Dynamic segments such as `[visitId]` are record identifiers. A screen or button becomes production-ready in the milestone indicated. User-facing copy and PDFs use Serbian Latin. Code, tickets and project documents use English.

## 1. Build order and completion gates

Implement one row at a time. Within a production row, ship a small path from screen to server to stored data and back to the screen. Give the next agent the last passing scenario and the first unfinished ticket.

| Milestone | Work in dependency order | What Jovan can do before moving on |
| --- | --- | --- |
| **M0. Validate the field journey** | Obtain anonymized examples and time one job. Build Today → visit → system form → submission summary → office review → customer preview with an in-memory fixture. Let the technician and office try it separately. Record where they hesitate and which information they look for on paper. | On a narrow phone, record two serviced systems, one requiring repair, and one inaccessible. The office can tell exactly what it must do next. Agree on field names and the sample report with pilot prospects. |
| **M1. Establish access and the runtime** | Initialize Next.js App Router and TypeScript, use the project's Docker-backed Supabase development stack, add migrations and two fictional organizations. Implement verified sign-in, recovery, workspace creation, invitations, role-aware navigation and row-level security (RLS). Build the Next.js production image. | Sign in as an owner, invite a technician, enter the correct workspace and sign out. Verify a different organization cannot read the first one's data through either the app or the Supabase API. |
| **M2. Complete one real visit online** | (1) Create a customer, site and systems manually. (2) Schedule a visit, select systems and assign a technician. (3) Open Today and save per-system outcomes, readings, parts and required follow-ups. (4) Submit, review, request a correction or open the customer preview. Connect the M0 screens to these features as each becomes available. | An owner schedules work. A technician submits it from a phone. The office sees the saved results and accurate preview in a separate session. Reloading either session preserves the work. A solo owner can perform the same handover. |
| **M3. Deliver an issued report** | Add private photo upload and verification, then freeze a customer-safe revision and queue a durable PDF render. Add render progress/retry, secure guest link, download, receipt, revocation and amendment. Connect actionable findings to their return visits or quote tasks. | Issue the report, open the link as a guest and acknowledge receipt. Correct a finding and issue revision 2. The revision 1 link still opens its original bytes until revoked. Retrying an interrupted render preserves the original revision. |
| **M4. Make fieldwork reliable offline** | Download assigned visit bundles and the app shell. Persist field edits and photo blobs on the device, replay operations with stable IDs, resolve conflicting edits and handle expired sessions or withdrawn assignments. Enable the offline controls on the field screens. | Download a visit, turn on airplane mode, edit two items, take a photo, close and reopen the app, reconnect and submit. The office sees each change once. Repeat with a conflicting edit and a reassigned visit. |
| **M5. Support repeat business** | Add spreadsheet preview/apply, maintenance plans, recurring visit generation, due and overdue queues, missing receipts, return appointments, manual billing review and owner CSV exports. Reuse the M2 register, scheduler and follow-up records. | Reimport a corrected spreadsheet, run the same recurrence twice and schedule a return visit from its finding. A second technician can see the first technician's history. The owner can export records that still join by stable IDs. |
| **M6. Run the paid pilot** | Deploy pinned Next.js, the worker and self-hosted Supabase to staging, then production. Configure HTTPS, public auth links, private service networking, persistent volumes, monitoring and backups. Enroll and bill pilot firms manually. | Restore database and files into an isolated environment, open a private photo and an archived PDF, then complete a real visit with a pilot firm. Compare field and office time with the M0 baseline and record paid continuation. |

## 2. First frontend ticket

**M0 implementation:** The six-view prototype is available at `/preview` during `next dev`; see [README.md](README.md) for the reset behavior, acceptance exercise and checks. It uses one in-memory session and does not implement the proposed production routes, authentication, persistence or PDF issuance. Technician and office review with pilot users remains outstanding.

Build the six views in the M0 row using the same example data. Keep the fixture and role switch in a development-only preview. Opening the prototype must never create real customers, issue reports or send messages. The prototype can start with a minimal Next.js scaffold that M1 keeps.

| System at Jagodina site `JA-02` | Technician's input | What office review must show |
| --- | --- | --- |
| KL-01 | Mark serviced and enter work performed. | One inspected system with a service result. |
| KL-02 | Mark serviced. Enter a measured zero in one applicable reading and leave another unmeasured. | Both readings retain their meaning and unit where applicable. |
| KL-03 | Mark repair needed. Record the damaged air deflector, the need for a quote, an accountable staff member and a deadline. | An inspected system and a quote task linked to the finding. |
| KL-04 | Mark no access. Record the locked archive, who will arrange access and the staff owner and due date for a revisit. | An inaccessible system and an open return action. No inspection or measurement is implied. |

Start with all four items pending. Keep the counters derived from the item outcomes. The completed example, `RN-2026-0142`, must show **4 planned, 3 inspected, 2 open actions**. The office can complete the handover even though two actions remain outstanding. Keep this example as a repeatable acceptance scenario through M6.

**Prototype review.** Hand the phone to the technician at “Danas” without explaining the controls. Ask them to find the right unit, record a locked room, and correct an entry. Ask the office user to identify the two next actions and locate the client-facing wording in the preview. Write down any confusion before building more screens.

## 4. What connects each screen to the rest of the app

| Feature | Implementation responsibility | Evidence of completion |
| --- | --- | --- |
| Identity and staff navigation | Supabase Auth, request-scoped server client, active membership, database and Storage policies. Apply role/assignment checks on every read, mutation and staff deep link. | Exercise owner, coordinator, assigned technician, unassigned technician and a second workspace against both normal UI and direct data access. |
| Register and assignments | Store customer → site → system → units and visit → visit items/assignees. Enforce same-site equipment selection, archive referenced records, preserve useful service history. | Start from a new workspace and schedule a real selectable system. Editing its current record preserves old visit and issued report history. |
| Field commands and office handover | Validate outcomes and transitions on the server. Keep readings, parts, evidence, source finding, due date and accountable owner together. Submit transactionally. Request corrections before issue. | Retrying submission yields one result and one task per intended action. Concurrent edits to different units survive. A stale edit to the same item requires resolution. |
| Evidence and customer reports | Reserve and verify private uploads. Render the same customer-safe data mapping in preview and PDF. Freeze the revision, enqueue work, archive bytes, validate every guest access and bind receipts to that revision. | Staff-only evidence never appears to guests. A worker restart completes the same revision. A later source correction produces a new revision with its own audit trail. |
| Offline persistence | Use IndexedDB for explicitly downloaded visit bundles, operations and photo blobs. Cache versioned shell assets separately. Isolate device records by user/workspace, store operation IDs and versions, sync on reconnect while the app is active. | Close/reopen offline, resume after session renewal, retry after a lost response and handle reassignment. Show whether the server has confirmed each change. |
| Recurrence, import and operations | Use stable occurrence and import keys. Run bounded recurring jobs, authorize exports, monitor failed jobs and back up both database and private objects. | Repeated jobs/imports do not duplicate records. After restore, staff can open the original issued PDF and its referenced evidence. |

**Runtime.** Run Next.js locally for development and Supabase in Docker. Read the active development stack's API URL and keys from its actual configuration. In production, run the Next.js app and worker in their own containers. They reach Supabase through the configured gateway on a shared private network. The browser uses a public HTTPS address. Keep SQL migration credentials and server-only keys out of the browser. Configuration and release instructions belong in [ARCHITECTURE.md](ARCHITECTURE.md).

## 5. Rules that affect multiple pages

- **Access and roles.** Owner and coordinator manage operational pages and issuance. Technicians work assigned visits and see the specific equipment history needed there. A guest can access only the revision identified by their link. Denied deep links and private downloads must reveal no other customer's details.
- **Export permission.** SPEC assigns the core CSV export to the owner. The coordinator row in DATABASE also mentions export. Implement owner-only for the full organization export in the pilot, test denial for coordinators, and align the two source documents when this decision is confirmed.
- **Visit status.** Use `scheduled → in_progress → submitted → issued`. Owner/coordinator can return a submitted visit to in-progress with a reason before issue, or cancel a scheduled/in-progress visit with a reason. Corrections after issuance create a new revision. Show rendering and sharing readiness separately from the visit status.
- **Outcomes and counts.** Start each visit item at `pending`. `serviced` and `repair_needed` count as inspected. `no_access` requires a reason and next action. Maintain the original planned set when an existing site system is added in the field. Show additional systems separately and include all inspected items in the inspected total. Include the planned/added distinction in the M2 schema and preview acceptance check.
- **Screen states.** For each data screen implement loading, empty, loaded, validation failure and recoverable server failure. Distinguish a denied/missing record from an empty list. Show actionable sync states on field screens and keep entered values after errors. Use keyboard operation, visible labels, large touch targets and text as well as color for statuses.
- **Pilot scope.** Manual enrollment and billing cover the pilot. Leave online checkout, tax invoices, inventory, regulatory certificates, a customer portal and enterprise dashboards for later decisions. The MVP's customer entry is the revision link.

## 6. How to hand one part to a coding agent

**First prompt to use**

> Read AGENTS.md, SPEC.md, FRONTEND.md, REPORTS.md and sections 1–3 of DEVELOPMENT_GUIDE.md. Implement only the M0 frontend journey for RN-2026-0142 using fictional, resettable in-memory data. Start on Today, open the visit, enter an outcome for each of the four systems, review and submit the summary, then open the office review and customer preview. Include validation for one pending item and one missing follow-up owner. Use Serbian Latin UI labels. Keep the fixture inaccessible in a production build. Verify the 4 planned / 3 inspected / 2 open actions result at phone and desktop widths. Report the changed files, checks you actually ran and the next M1 ticket.

**First production tickets after feedback**

1. **M1a — Runtime and identities.** Implemented auth entry screens, verified sessions, recovery, the protected `/account` landing, additive identity migrations, opt-in development fixtures and a non-root standalone app image. See [README.md](README.md) for setup and verification. Workspace creation, invitations, selection and operational navigation remain M1b. SMTP delivery and production public-origin configuration must be checked on the target stack.
2. **M1b — Workspace isolation.** Implemented resumable workspace creation, copyable verified-email invitations, membership/last-owner commands, workspace switching and role-specific staff shells. Invitations are manually delivered links, not SMTP messages. See [README.md](README.md) for the normal workflow and [DATABASE.md](DATABASE.md) for command isolation. Real register/visit assignments follow in M2a.
3. **M2a — Register to assignment.** Implemented create-only customer/site/system register, transactional scheduling, assignments, office schedule and technician Today. See README for the normal flow. Outcome entry and submission remain M2b.
4. **M2b — Assignment to office preview.** Connect the validated field form, submission, follow-ups and office review to server commands. Complete the four-system scenario online and open the preview from a separate office session.
5. Continue with M3 through M6 in section 1. Split each milestone when the next user-visible result can be demonstrated independently, for example “issue and recover a failed render” before “share and acknowledge a revision.”

**Handoff for each pull request.** Cite the milestone and SPEC requirement (P01–P09), the affected route, the role and the data change. Give a short reproduction path and expected on-screen result, report the checks actually run and list the next unfinished dependency. Verify phone and desktop behavior for changed UI, isolation for access changes, rendered pages for PDF changes, and reconnect/retry behavior for offline changes. Run the relevant scripts present in the repository. A passing fixture exercise demonstrates the prototype. The production gates above require real sessions, persisted data and the indicated failure checks.
