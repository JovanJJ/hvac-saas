# Database model and access rules

PostgreSQL stores operational records, tenant boundaries and immutable report snapshots. Auth identities are supplied by Supabase Auth. Use SQL migrations for schema, constraints, grants, RLS and private Storage policies. This is the target schema for the milestones in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

## Entities and ownership

Use UUID primary keys, `timestamptz` for instants, calendar dates for due dates, decimal values with explicit units for measurements and integer minor units plus currency for any future money fields. Tenant-owned tables carry a non-null `organization_id`. Mutable records written offline also have a monotonic integer `version`. Record creator/editor and timestamps where they establish accountability.

| Entity | Key fields and relationships |
| --- | --- |
| `organizations`, `memberships`, `invitations` | Organization has display name and time zone (pilot default `Europe/Belgrade`). Membership links `auth.users` to organization, role and active status. Unique org/user. Invitations fix organization, intended email, role, expiry and accepted state. |
| `customers`, `sites` | Customer belongs to organization; site belongs to customer. Site has stable code, name, address, optional contact, time zone and separate staff-only access notes. |
| `systems`, `units` | System belongs to a site; unique normalized system code per site, room/position, type, optional manufacturer/model. Units belong to a system, with indoor/outdoor role, optional serial and model. Keep a stable system ID when a physical component is replaced. Archive old units and preserve visit history. |
| `maintenance_plans`, `plan_systems` | Site, local start date/time, interval in months, enabled state and covered systems. Generate one visit per plan and local occurrence date. An administrator can pause future generation while retaining prior visits. |
| `visits`, `visit_assignees` | Site, optional plan, local occurrence date, type, time window, lifecycle state, actual times, creator and version. Assignees are active org members. Billing-review flag is an office decision separate from completion and customer receipt. |
| `visit_items` | One system per visit, location and org must match. Store outcome, work performed, finding, reason for no access, public notes and version. Permit several assigned technicians to work on different items. |
| `readings`, `part_usages` | Children of visit item. Reading has kind, context/mode, status, value and unit; a measured value can be zero. Part has name/code, quantity and unit. Preserve captured descriptions even if catalogs change. |
| `attachments` | Item, storage provider and object identifier (Cloudinary authenticated image or private PDF Storage path), file type/size, caption, visibility, upload state, author. Only verified uploaded objects may appear in an issued report. |
| `follow_ups` | Source visit item, type (quote, repair or revisit), responsible staff member, optional customer action, deadline, state. A revisit may link to a new visit; retain the original finding. |
| `report_revisions`, `report_links`, `report_receipts` | Unique visit/revision; report number, snapshot, template version, issuer, reason for amendment, artifact state/path/checksum. Link records store token digest, expiry and revocation. Receipt records refer to the exact revision and link. |
| `import_batches`, `mutation_receipts`, `jobs`, `audit_events` | Import preview and content/mapping digest; operation UUID, payload hash and result; durable jobs with stable dedupe key, lease and retry state; critical changes with actor and time. Keep idempotency records at least as long as the supported offline retry period. |

## Enforce relationships at the database

- Add unique `(organization_id, id)` keys for tenant parents and composite foreign keys from children. For a visit item, enforce the same organization **and site** using composite references to both visit and system. Changing a parent site once it has history requires a deliberate transfer workflow; archive and create a replacement for the pilot.
- Constrain `(organization_id, visit_id, system_id)`, `(organization_id, visit_id, revision_no)` and the plan occurrence key. Allocate human-readable work order numbers under a per-organization/year counter or an equivalent concurrency-safe mechanism. Revisions share the work order number.
- Visit outcomes use `pending`, `serviced`, `repair_needed` and `no_access`. Submission requires at least one item and no pending items. Inspection count includes serviced and repair_needed. A no-access item carries a reason and cannot claim a measured reading or completed inspection. Each outstanding item has a linked follow-up with an accountable staff owner and deadline; the customer may be the next person expected to act.
- Set reading value and unit when measured. For `not_measured` or `not_applicable` store a null value and optional note. Keep private notes and public report text in explicitly separated fields or relations; RLS alone cannot hide individual columns.
- Archive operational parents referenced by visits. Foreign-key restrictions and immutable revision snapshots preserve history. Do not cascade organization/member removal into previously issued evidence as a routine UI action.
- Index all tenant/relationship keys used in access policies and common queries: assigned visits by date, systems by site and normalized code, units by serial, open follow-ups by due date, due plans, and claimable jobs by status/time.

## Access model

Enable RLS on every exposed tenant table, including relationship tables. Base policies on `auth.uid()`, active membership and, for field records, visit assignment. Keep membership lookup helpers free of recursive RLS evaluation. Organization selection in the UI is context, never proof of membership.

| Caller | Read | Write |
| --- | --- | --- |
| Owner | All organization work and staff | Membership, operations, report issuance and sharing. Preserve at least one active owner. |
| Coordinator | Organization operations and roster needed for scheduling | Register, plan, assign, review, export, issue and share; membership changes reserved for owner. |
| Technician | Assigned visit bundle, necessary site information and service history of the systems on an assigned visit | Findings, readings, photos, follow-ups and field submission for editable assigned work. |
| Recipient | One frozen revision via validated, revocable token | An acknowledged receipt for that revision, by explicit action only. |
| Worker | Minimal queued job context and required snapshots/files | Claim/complete jobs and maintain render or recurrence state. No general browser-accessible job endpoint. |

Keep tables supporting invitations, idempotency, jobs, tokens and audit in a non-exposed schema or deny access to API roles. For stateful/transactional operations expose narrow RPCs instead of granting raw client updates to lifecycle state. If a function needs elevated execution, give its owner minimum privileges, fix its search path, schema-qualify names, explicitly check the actor, revoke default PUBLIC execution and grant only the needed entry point. Apply equivalent authorization to private Storage upload/download paths. A path prefix is only a locator.

## Migration and verification

M1 implements `organizations` and `memberships`, plus private workspace-creation receipts, invitations and identity audit events. Both have RLS and authenticated read grants; memberships expose only the caller's own active rows. A fixed-search-path membership predicate in the non-exposed `hvac_private` schema permits reading only organizations with active membership. Browser/API roles have no insert, update or delete grants. Organization creation, invitations and staff mutations are M1b RPC commands; the application does not use `DATABASE_URL` to bypass user policies.

M1b adds optimistic `version` columns and narrow public RPCs. `create_workspace` atomically creates the organization and owner membership and binds an actor/operation UUID to its canonical payload and result. `update_workspace_member` and `update_workspace` require the caller to remain an active owner after obtaining an organization lock. Competing owner changes serialize, preserving at least one active owner. Stale versions fail with terminal HTTP 409 (`PT409`, migration 012); raw table writes remain denied.

Private invitations bind organization, normalized email, role, token digest, issuer, expiry and acceptance/revocation state. Creation retries reuse the same operation and digest; reissuing supersedes a pending invitation. Acceptance requires a live verified identity with the intended email, locks the organization and invitation, and changes membership plus acceptance/audit state atomically. Accepted-link replay never reactivates a revoked member. Token-bearing responses never include the digest; anonymous lookup exposes only the company name, role and expiry for a currently valid pending token.

Lifecycle RPCs run as a non-login, non-inheriting executor without Auth-schema or RLS-bypass privileges. RLS permits only that executor to perform its narrow table writes. The self-hosted Auth schema does not permit the migration role to delegate Auth grants: private, fixed-search-path identity bridges owned by the existing database administrator return only the verified caller, their email, or a roster explicitly authorized for the requested organization. These helpers are not exposed RPCs. Migrations temporarily acquire function-owner authority, lock down effective execution grants, and revoke that authority before commit. Only the token-preview RPC permits anonymous execution.

Use `npm run db:migrate` against the intended server-only `DATABASE_URL`. The runner loads the ignored environment files, takes a transaction advisory lock, checks SHA-256 migration checksums and records applied files in non-exposed `hvac_migrations.applied`. A retry skips matching files; changed applied files or failed SQL roll back. Add a new ordered SQL file for each subsequent change. Never reset the existing self-hosted stack.

For development only, set `ALLOW_DEVELOPMENT_SEED=true` and a locally generated 12–72 byte `SEED_PASSWORD`, then run `npm run db:seed`. The seed creates two fictional organizations and owner A, technician A, owner B, unassigned and unconfirmed identities under `hvac.example.invalid`. Repeated seeds preserve passwords, membership state and existing fixtures; ID/email collisions fail atomically. These raw Auth inserts target the inspected GoTrue development schema and are not a production identity-provisioning API. Run `npm run test:db` for rollback-only policy tests against these fixtures. Tests temporarily revoke one fixture membership and roll back that change. Future visit-assignment policies are not yet implemented.

Review migration SQL in version control and stage changes before production. Back up and release as described in [ARCHITECTURE.md](ARCHITECTURE.md).

Test with two organizations, an unassigned and an assigned technician, a coordinator and a revoked member. Exercise both direct Supabase access and Next.js entry points. Include mismatched site/system, concurrent revisions, repeated recurrence, reimport, a zero reading, null readings and snapshot preservation after source data changes.

References: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage policies](https://supabase.com/docs/guides/storage/security/access-control), [database migrations](https://supabase.com/docs/guides/deployment/database-migrations).

## M2a register and scheduling

Migrations 005–006 add customers, sites, systems, scheduled visits, visit items and assignees. Composite foreign keys enforce organization/site relationships. Normalized uppercase site codes are unique within an organization; system codes are unique within a site. M5a adds versioned editing, archiving and component units as described below. M2b adds field outcomes and handover below.

`save_operation(organization, operation, kind, data)` requires an active owner/coordinator and serializes against membership changes using the organization lock. Its actor-scoped operation receipt binds the exact payload to its generated entity ID; equal retries return the existing result, changed payloads conflict. Visit creation atomically writes the visit, distinct planned systems and active assignees. Site-local start/end timestamps are converted to instants using the site's IANA time zone. Nonexistent start times are rejected; ambiguous local times currently use PostgreSQL's standard-time interpretation. Recurrence/DST anchor rules remain M5.

Raw tables grant office-scoped SELECT only; authenticated direct writes remain denied. `operation_snapshot` is an authenticated, organization-scoped DTO read: office staff receive the register and schedule, technicians receive only assigned visits and relevant site/system details, with no organization-wide register. Active membership is checked again on every read. Today filters to the caller's assignments on the current site-local date. No application query uses SQL migration credentials.

## M2b findings and submission

Migrations 007–011 add visit/item versions, captured work/findings/internal notes, reading and part arrays, author/time attribution, follow-ups and online lifecycle commands. For this bounded online slice, readings and part usages are validated JSONB children on the versioned item, rather than separate tables. Values retain explicit status, context and unit; non-measured readings have null values. `follow_ups` has one open action per source item, with composite organization foreign keys to its source and accountable membership. Incomplete draft owners/deadlines are nullable; submission requires both and rechecks active membership. Multiple actions per item remain future work; M3g adds office completion and return scheduling below.

All business tables retain RLS and deny direct authenticated writes. Technicians read authorized visit bundles through RPCs, not organization-wide tables. Commands serialize with membership changes and submission under organization/visit locks; receipts prevent duplicate actions and item versions reject stale overwrites. Private `visit_corrections` retains the actor, reason and timestamp after the current correction banner clears on resubmission. `visit_staff` is a non-exposed, fixed-search-path identity bridge owned by the database administrator, scoped to a currently authorized visit; the executor still has no general Auth-schema access. Rollback tests include another organization, an active unassigned technician, revoked membership, zero/null readings, stale versions, receipt mismatch, missing owner, pending items, locked submissions and correction return.

Migrations 011–012 use `PT409` for expected domain conflicts in visit and workspace commands. They must return immediately rather than trigger PostgREST transaction retries for SQLSTATE `40001`. See the [Supabase guidance](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b).

## M3a private photo evidence

Migrations 013–017 add `attachments` with source visit/item, organization, captured author, immutable reservation metadata, explicit customer/internal visibility, reserved/verified/removed state and verified provider identity/version/format/dimensions/size. Composite foreign keys enforce tenant ownership and that the source item belongs to the specified visit; the reservation command checks that relationship before insertion. Raw authenticated writes are denied under RLS. Office table reads are organization-scoped, while technicians receive only authorized `attachment_read` bundles.

`attachment_command` locks organization then visit, checks live membership/assignment before replay and increments the visit version on effective evidence changes. It reuses a stable UUID for identical reservations/completion and keeps removal tombstones. `visit_command` now rejects submission with reserved attachments. Removed or unverified images never enter the customer mapping. Cloudinary normalization can change stored bytes, so `expected_bytes` describes the incoming file and `verified_bytes` describes the verified object served by the app.

The private `evidence_verifier` key has no API-role grants. SQL tooling provisions its matching runtime secret; completion checks a bounded-lifetime HMAC of verified metadata bound to actor, organization, visit and attachment. The narrow executor receives read access to this key and crypto schema usage, without general Auth access, SQL credentials or RLS bypass. Tests cover forged completion, denied direct writes/key reads, duplicate reservations/completion, pending-photo submission, removal, another organization, an active unassigned technician and revoked membership.

## M3b first report issuance

Migrations 018–022 add `report_revisions` and the private `report_counters`, `report_issue_receipts` and `render_jobs` tables. Revisions have composite organization/visit foreign keys and unique organization/visit/revision and organization/report-number/revision keys. RLS grants office-scoped SELECT only; the non-login executor can SELECT/INSERT revisions but cannot UPDATE/DELETE them. No raw API role can create or change revisions or read/mutate private queue/counter/receipt tables. Privileged SQL tooling retains maintenance access for development fixture cleanup and migrations.

`issue_report` authorizes an active verified owner/coordinator under the organization lock, then locks the visit and revalidates all findings, follow-ups and attachment eligibility. First issuance requires the submitted aggregate version. The same actor/operation UUID binds visit and base version; mismatched reuse returns `PT409`. Different first-issue operations for an already issued visit return its existing revision 1 rather than allocate again. Authorization precedes both retry paths. Creating revision 1 atomically advances an organization/year counter, freezes the single allowlisted DTO and verified customer-visible evidence references, inserts a uniquely keyed queued render job and records issuance/audit metadata. The year follows the organization's IANA time zone at issuance; sequences have a minimum of four digits and never reuse a committed number.

`report_preview` serves the live allowlist until issuance, then the stored snapshot. `report_revision` and `report_list` expose only office-authorized snapshots and limited queue state. M3c manages queue leases and render completion/retry; readiness is not stored by mutating the immutable snapshot. Issued visits reject field saves, added systems, pre-issue correction returns, new photo reservations/completions and removal of verified photos. Historical successful command retries remain idempotent. Draft writes and issuance both reject malformed nested reading/part types and values outside finite report-consumer bounds. Customer/private-note filtering is tested at the canonical SQL boundary, including nested readings/parts and evidence, rather than against the removed TypeScript mapper.

### M3c PDF leases and archives

Migrations `202611160023`–`202611160024` add private render leases/attempts, a worker identity, immutable artifact metadata and retry receipts. Claims use `FOR UPDATE SKIP LOCKED`, a random token, a 120-second lease and a 30-second heartbeat. Three attempts with bounded backoff require an explicit office retry afterward. A retry retains the same job/revision and write-once SHA-256/size/renderer manifest. Runtime roles cannot update/delete artifact rows or snapshots.

The private PDF-only `report-pdfs` bucket is installed separately through the Storage owner, guarded by the database installation UUID. The migration principal does not own Storage tables. Worker SELECT/INSERT requires an active claim and manifest for the exact fixed revision path; office SELECT requires an active office membership and ready artifact in the same organization. Restrictive policies prevent unrelated broad policies bypassing these restrictions. Guest access is the narrowly scoped M3d exception; runtime overwrite/delete remains denied. See README for `worker:configure` and operator-only Storage maintenance.

### M3d capability links

Migrations `202611170025`–`202611170026` add private, RLS-protected `report_links`: organization/revision composite FK, unique token digest, actor/operation uniqueness, created/expiry time, bounded TTL and revocation actor/time. API roles have no raw table access. `create_report_link` and `revoke_report_link` require a currently verified owner/coordinator and serialize on the organization; creation requires a ready job plus artifact. Replay compares revision/digest/TTL and preserves identity/deadline. `report_links` exposes all scoped status metadata without digests, preserving access to older links for revocation. Audit records carry link IDs, never raw tokens.

`guest_report` accepts a raw 43-character base64url capability and hashes it inside the security-definer boundary; a stored digest cannot be replayed as the bearer token. It returns exactly the ready frozen revision, its approved evidence references and archive metadata, or null for unavailable links. No receipt or view audit is written. Existing link targets do not follow a visit's latest revision.

The guarded Storage-owner setup installs anonymous SELECT policies using `guest_pdf_read`: a valid `x-report-token` header must match the object's ready artifact and the live link. The installed Storage API supplies transaction-local `request.headers` and `storage.operation`; only `storage.object.get_authenticated` is allowed. Restrictive policies deny broader list/sign/S3/metadata access and guest writes even if an older permissive policy exists. Anonymous API clients still cannot name private-schema helpers directly. This contract was exercised through the actual Storage API; keep those tests when upgrading the self-hosted distribution. No service-role key enters guest runtime.

### M3e receipt records and permissions

Migrations `202611170027`–`202611170028` add private `report_receipts` with a unique link, a composite organization/link/revision FK, trimmed name/role (1–120 characters), `confirmed_at`, fixed method and statement version. The executor can SELECT/INSERT but cannot UPDATE/DELETE. API roles have no raw table grants. The receipt row is guest audit evidence; staff `identity_events` requires a verified Auth actor and is not populated with an impersonated issuer for a guest action.

`acknowledge_report` accepts the raw capability, name, role and explicit true consent, deriving all identifiers inside the database. It locks organization then link, rechecks deadline with the current server clock after waiting, rejects revoked/not-ready links, and returns the existing row only for a matching replay. Changed recipient details return PT409. This serializes competing submissions and revocation, preserves the original timestamp and never redirects the receipt to a newer revision.

`guest_report` includes only that live link's receipt. `report_receipts` requires a current verified owner/coordinator and scopes every read by organization/revision; it retains historical receipts after link revocation. No report snapshot, archived artifact, operational visit/follow-up or billing state is changed.

### M3f amendment transactions

Migrations `202611170029`–`202611170031` add private `report_item_bindings`, append-only `report_amendments` (predecessor, reason, actor/time, before/after item corrections), actor/operation-scoped amendment receipts, and separate `visit_items.corrected_by/corrected_at`. Runtime has no UPDATE/DELETE on snapshots, amendment audit or bindings. Bindings backfill old revisions only on a complete frozen-code/current-item match; first issuance now captures the exact stable item IDs/positions. The report DTO does not gain operational item IDs.

`amend_report` locks organization then visit, reauthorizes current office membership before replay, compares a canonical payload hash, enforces the latest base/aggregate and item versions, and requires exactly every bound item once. Input is bounded to 500 systems / 512 KiB and a 1–2000 character reason; protected identity/evidence/author keys cannot be supplied. Operational updates are revalidated through the same private validator as initial issuance. Any failure rolls back all item/action writes. Matching retries return the committed revision; changed payloads or stale competing operations conflict. A unique predecessor prevents forks.

The canonical reading/material projection is reused for initial issue, amendment input and new snapshot generation. Equivalent public values preserve existing private metadata. New snapshots retain predecessor identities/photos, calculate totals from validated findings, record v2 template/issuer/time and enqueue one job. Original entered-by/time and internal notes survive; the separate correction fields/audit identify office changes. The visit version advances while status stays issued. Revision history/latest reads remain organization-scoped. Old links/artifacts/receipts are not updated, and the report counter is not advanced for an amendment.

### M3g action lifecycle

Migrations 032–035 extend the existing one-action-per-item model with version, first office-management time, completed state/actor/time/internal note, historical owner label and a unique tenant-bound return visit. Private `follow_up_events` is append-only for the runtime; actor-scoped `follow_up_receipts` bind the full operation payload; `follow_up_bookings` enforces one canonical booking per source action. Raw authenticated writes remain denied, and composite foreign keys retain tenant/source/return integrity.

Office changes increment action, item and aggregate versions. Shared `save_captured_follow_up` prevents field corrections or report amendments from deleting/replacing an office-managed action. Open actions require active owners for submission/issuance; completed actions keep their former owner's captured label. No lifecycle command writes report revisions, artifacts, guest links or receipts. Follow-up list filters and broader operational queues remain M5g.

### M4a assigned offline reads

Migrations 036–037 add `offline_visit_bundle(organization, visit)` and `offline_assignment_ids(organization)` as verified, fixed-search-path, session-scoped RPCs owned by the existing restricted executor. The bundle requires an explicit active assignment even for office roles. The inventory exposes only the active caller's own assignment IDs. Anonymous/service-role execution is not granted; other-tenant, unassigned and revoked membership reads are denied. No business table or write permission is added.

Bundle schema 1 reuses `visit_bundle`, removes unrelated available systems, allowlists reading/material values through the shared projection helpers, and includes only the existing narrow return-source history plus a photo count. It preserves field/correction authorship, versions, action lifecycle and zero/null values. Device records live in separately partitioned IndexedDB, as described in [FRONTEND.md](FRONTEND.md), not in new server tables. `offline_visit_bundle.sql` extends the rollback suite with assigned, unassigned office/technician, second organization, revoked and anonymous cases.

### M4c durable replay acknowledgements

Migration 038 adds private `field_replay_receipts`, keyed by organization, verified actor and operation UUID. It stores canonical command data and the original safe acknowledgement atomically with the existing `visit_command` changes. The authenticated-only `replay_field_command` RPC accepts save/submit, locks organization then visit, requires current active membership plus explicit assignment, and reauthorizes before returning a receipt. Same-key changed payloads return PT409. Existing item/aggregate versions, author capture, managed-action protection and submission validation remain authoritative. The receipt is private and is not directly readable by staff, anonymous or service-role API clients. Retain receipts for the supported offline retry period; no automatic expiry is introduced here.

Device schema 3 adds pending submissions and records attempted operations before sending. Per-operation acknowledgement/removal is one IndexedDB transaction; failure preserves the original operation for retry. See [FRONTEND.md](FRONTEND.md) for queue and identity rules. `field_replay.sql` covers original-result replay after submission, stale/mismatched commands, attribution/zero values, tenant and unassigned/withdrawn/anonymous denial.

### M4d photo phase receipts and device blobs

Migration 039 adds private `photo_replay_receipts`, keyed by organization, verified actor, attachment UUID and phase (`reserve`, `complete`, `remove`). Authenticated-only `replay_photo_command` locks organization then visit, requires explicit active assignment and captured ownership, reauthorizes before replay, and delegates all domain transitions to `attachment_command`. Canonical completion data excludes renewable `proof`/`expires`, while the first completion still validates its HMAC and deadline. A mismatched same-phase logical payload conflicts.

Each receipt preserves the original acknowledgement and cumulative own phase effects (zero/one aggregate-version increment per phase). This lets the device recover a lost completion or concurrent removal without double-counting versions or reviving a tombstone. Unknown removals reserve/remove atomically under the same attachment ID and retain their effects. Original field command receipts and immutable report snapshots are unchanged. Private receipts are not directly readable through staff/anonymous/service-role APIs.

IndexedDB schema 4 preserves prior bundles/drafts/submissions and adds partitioned `photos` containing Blob, caption/visibility, attribution, stable ID, intent, attempted timestamp, phase effects and recoverable errors. Acknowledgement updates the photo/source bundle and unattempted submission version in one transaction. Failed acknowledgement writes retain the Blob and retry the original phase. See [FRONTEND.md](FRONTEND.md) for lifecycle/cleanup boundaries. `photo_replay.sql` extends rollback checks with expired-attestation renewal, idempotent phase/version effects, tombstones, pending-evidence submission denial and assignment/tenant isolation.

### M4e reconciliation and retained device work

Migration 040 adds private `field_reconciliations` and authenticated-only `field_recovery_context` / `reconcile_field_command`. Both RPCs use the same organization/visit lock order and current verified explicit-assignment check before snapshot or receipt access. Snapshots reuse the offline allowlist and expose only safe evidence metadata. Actor-scoped exact receipt equality distinguishes committed, absent and mismatched operations; photo acknowledgement effects can be recovered without duplicate upload/version counts.

Reviewed writes require a fresh operation UUID, predecessor UUID and explicit current item/aggregate base version. They delegate to the existing replay/visit command and store actor, exact logical payload and a safe server-before snapshot atomically. The new operation's retry returns its original result; a changed predecessor/payload, committed predecessor, stale review, withdrawn access or finalized record cannot become a blind overwrite. Private audit rows remain inaccessible through staff/anonymous/service-role table APIs. `field_reconciliation.sql` checks independent technicians on separate items, same-item drift, reviewed writes/retries, aggregate recovery, lost acknowledgement lookup and tenant/unassigned/withdrawn/anonymous denial.

IndexedDB schema 5 preserves all prior stores and adds partitioned `blocked` source copies plus `recoveries`. Withdrawal hides pending source data while retaining authored drafts and photo Blobs. Explicit reviewed adoption/replacement archives the original operation (and cancelled handover) without changing its ID/payload. Reauthorization can restore the same partition but never automatically rebase a version conflict. M4f implements atomic device-history cleanup/discard without a server schema change. See [FRONTEND.md](FRONTEND.md).


M4f retains IndexedDB schema 5 and server migrations through 040. Device cleanup removes all seven private stores' contents (including active metadata, withdrawn bundles and recovery history), scoped to a visit/partition for ordinary removal/discard or explicitly to all accounts for shared-device cleanup. The same transaction checks pending/attempted records before deleting. Server replay/reconciliation audits and business records are unaffected. See [FRONTEND.md](FRONTEND.md).


### M5a equipment maintenance and history

Migrations 041–042 add monotonic versions, archive/editor timestamps and editor identity to customers/sites/systems, site contact, and optional system manufacturer/type. Existing parent IDs, site relationships, visit items and legacy model/serial values remain intact. No transfer or hard-delete workflow is added. `units` carries organization/system composite keys, indoor/outdoor role, manufacturer/model/serial, creation/edit/archive timestamps, version and an optional same-system `replaces_id`. A replacement archives the old row and inserts a new ID in one transaction; archived units cannot be edited or revived. Current system metadata and component metadata are independent.

`register_command` serializes on the organization lock, rechecks verified owner/coordinator membership, compares the entity version and binds the actor/operation ID to exact inputs in private append-only `register_events`. Equal retries return the same result; changed retries and stale edits return PT409. Component creation checks the parent system version; replacement compares the component version and preserves the system ID. Raw browser register/unit writes remain denied. Units permit office-scoped SELECT only; technicians use the narrow history RPC. Existing create operations use explicit columns and retain their actor-scoped receipts.

Archiving is reversible for customer/site/system records and does not cascade archive flags or delete existing work. Insert triggers reject new child records, visits and visit items under archived ancestors. Existing scheduled/recorded items can still be completed. Restoring an ancestor does not override a child's own archive flag. Parent transfer remains excluded. Editing a site time zone does not move existing visit instants.

`register_detail` scopes every read to the requested organization. Office staff can read customer/site/system details, children, components and submitted/issued service history. A technician must have an active membership with an explicit visit assignment containing the exact system; sibling systems and customer/site details are denied. Authorized history includes work, findings, no-access reasons, allowlisted readings/materials, field attribution/correction time and follow-up state. Internal notes, arbitrary JSON metadata and private delivery URLs are excluded. Field history does not grant access to the complete previous visit or its photos. Assignment withdrawal/revocation is checked on every read. Issued snapshots, archives and links remain immutable.

The rollback suite `equipment_register.sql` covers replay/stale replacement, retained old components, immutable issued data, archived-parent restrictions, zero preservation, owner/coordinator access, denied raw writes and technician/unassigned/cross-tenant/revoked/anonymous boundaries. Browser acceptance additionally compares the original PDF checksum and races competing replacements.
