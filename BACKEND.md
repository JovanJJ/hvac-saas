# Backend contracts

Use request-scoped Supabase SSR clients and a small server-only data-access layer. Reuse command validation and authorization across Server Actions, Route Handlers and mobile replay. Server Components call the data-access layer directly for reads. This document defines the wire contracts required by the PWA and guest links; internal TypeScript names may evolve.

## Identity and workspace entry points

`/sign-in`, `/sign-up`, `/forgot-password` and `/reset-password` use validated Server Actions. `proxy.ts` refreshes cookie sessions; the DAL independently uses Supabase `getUser()` and requires a confirmed email. Do not authorize from `getSession()` alone. Auth uses the public client key under the caller's session; database migration credentials never participate in runtime requests.

`/account` lists the caller's own active memberships and selects a workspace. `/` resolves the role-specific landing (`/office` for owners/coordinators, `/today` for technicians, `/onboarding` for accounts without memberships). A per-user HTTP-only workspace cookie is only a preference: all staff entry points resolve membership again and protect reads near their data source. Missing/revoked membership and disallowed deep links reveal no operational data.

Workspace creation, identity updates, invitation creation/acceptance/revocation and membership changes are validated Server Actions backed by narrow database RPCs. They execute with the verified caller's Supabase session; the app never uses SQL migration credentials or a service-role client for tenant commands. Creation/invitation operation IDs make retries idempotent, and versions make competing updates explicit. Owner commands authorize again under the organization lock; concurrent last-owner changes cannot both succeed.

The owner-only team page creates copyable invitation links for manual delivery. No email is sent by invitation creation. `lookup_workspace_invitation` accepts a token digest and returns limited current preview metadata; `accept_workspace_invitation` independently checks current verified email, expiry and revocation before atomically joining the organization. Reissue creates a new random token and revokes the old pending link. Active existing members retain their current role; an accepted link cannot restore revoked access. Role/active-state updates use explicit membership commands.

`workspace_roster` is scoped to active owners/coordinators; coordinators receive active staff only. `workspace_invitations` and company/team settings are owner-only. Membership lists available by direct table access remain self-scoped. Private audit rows record actor, organization, event type and target identifier without raw tokens. Visit assignment and private-file rules remain later milestones.

`/auth/confirm` accepts allowlisted signup/email/recovery token hashes and strips them by redirecting to a fixed destination. `/auth/callback` exchanges a PKCE code and permits only allowlisted staff routes and high-entropy invitation paths as the next path. Configure the existing stack's email templates and redirect allowlist per [README.md](README.md). Pending signup must preserve the SSR PKCE verifier: call sign-out only if signup actually returned a session. The development mail overlay and real email-link regression are described in [README.md](README.md). Recovery responses do not disclose account existence. A verified signed-in user may also change their password via `/reset-password`; the update ends their Supabase sessions and returns to sign-in. Failed/expired verification links return a recoverable message without provider error details.

All session cookies are HTTP-only and SameSite=Lax, with Secure on HTTPS. Auth responses use private/no-store caching. New-password validation requires at least 12 characters and at most 72 UTF-8 bytes. Provider-side Auth throttling and outbound email configuration remain required. Next.js Server Function argument logging is disabled, and token-bearing callback, invitation and sign-in/sign-up requests are excluded from development access logs. Configure equivalent redaction at the production reverse proxy.

## Requests and permissions

Authenticate each staff entry point, verify the session/claims on the server, then resolve active organization membership. Check the role and visit assignment at the point of mutation. Validate IDs, enums, input lengths, allowed transitions, upload size/type and permitted report fields. Return UI-specific DTOs. User-initiated operations run under the user's authority. The worker and guest-report service use narrowly scoped server-only access paths. Do not trust a client-provided author, role, tenant label, storage path or verification status.

| Entry point | Consumer and contract |
| --- | --- |
| Server Actions for invitations, register edits, scheduling, imports, sharing and office review | Staff web UI. Validate the command and return field errors or a typed success result; revalidate only affected views. Authenticated users may accept a valid invitation matching their verified identity. |
| `GET /api/field/visits/:id` | Assigned staff. Returns a minimal, versioned offline bundle with scheduled systems, public/internal fields appropriate for the technician and relevant system history. |
| `POST /api/field/sync` | Assigned staff. Bounded ordered batch; each operation has `operationId`, `entityId`, `baseVersion`, `type` and `payload`. Respond with a result for each operation; acknowledge successful earlier operations independently. |
| `POST /api/field/attachments/prepare` and `/complete` | Authorize item and visibility, reserve an object ID and issue a short-lived private upload permission. Complete verifies stored object metadata and makes it available for the item. Retrying with the same ID reuses the reservation. |
| Report preview / issue / amend | Issuer (owner/coordinator). Preview uses the same template as issuance; issue/amend freezes data transactionally and returns a revision ID and render state. The office can see render errors and retry the same revision. |
| `GET /r/:token` and `POST /r/:token/receipt` | Guest. Validate token digest, expiry, revocation and revision on each request. Serve that revision privately. POST accepts an explicit acknowledgement and name/role; replay returns the existing acknowledgement for that link. Ordinary page views have no receipt side effect. |

Use `401` for missing or expired authentication, `403` for disallowed actions on a known visible record, `404` for inaccessible object identifiers, `409` for a stale version or mismatched idempotency payload, and `422` for invalid domain input. A successful sync batch may include per-operation conflicts. Sensitive GET responses and public report downloads use private/no-store caching. Public links have high-entropy random tokens, a configurable expiry and a revocation action. Redact tokens from app and proxy logs.

## Visit lifecycle

| Transition | Conditions and effects |
| --- | --- |
| `scheduled → in_progress` | Assigned technician or operational staff starts the visit. Preserve actual start time. |
| `in_progress → submitted` | Actor is assigned or authorized office staff; every included system has an explicit outcome. Validate follow-ups, timestamps and attachment completion. Commit outcomes and tasks consistently. |
| `submitted → in_progress` | Before issue, owner/coordinator requests a correction with a reason. Field editing resumes. |
| `submitted → issued` | Authorized office actor freezes the snapshot, visit/report number and new revision, and enqueues the PDF render in one transaction. The report can be shared when rendering succeeds. |
| Amendment of issued visit | Authorized issuer supplies a reason and explicit corrections; validates a complete replacement snapshot, appends a new revision referencing the previous revision and updates the latest pointer atomically. Keep old bytes, tokens and receipts bound to their revision. Record corrected operational values/history in the same transaction. |
| Cancellation | Owner/coordinator may cancel a scheduled or in-progress visit with a reason. Preserve recorded work for staff review; remove future assignments from the active schedule. |

In Solo mode the owner may both submit and issue. A field device can queue a submission offline, but only a successful server response marks the visit as submitted. Office review for billing, client receipt and quote approval are independent events. Quote approval and invoice issuance are outside the MVP.

## Replay, jobs and failure handling

1. Scope an operation key to organization, actor and operation UUID. In a database transaction, lock/check the receipt, compare the canonical payload hash, enforce current access, check version, write domain changes and persist the result. A retry with the same payload returns the committed result to a still-authorized caller. A different payload under the same key returns a conflict.
2. Version visit items independently. Two technicians editing different systems can both succeed. Stale edits to the same item return the current safe values/version and allow manual reconciliation. A final submission validates the aggregate and child versions; lock the visit consistently during finalization and writes to prevent late changes slipping into the snapshot.
3. Keep failed photo blobs locally until confirmed. Submit only after required uploads complete or a user explicitly removes the unsubmitted attachment. Show terminal file-validation failures with a recovery action.
4. Use transactionally enqueued jobs with unique logical keys. Workers use a lease, bounded retries/backoff and a visible failed state. Use a deterministic private path for a given revision, conditional writes and a recorded digest so retries cannot replace a different PDF. Share only verified ready artifacts.
5. A maintenance recurrence is keyed by plan and intended local date. Generate a bounded forward window. Preserve existing attended/issued visits when a plan changes. For a monthly date absent in the target month, clamp to month-end while retaining the original anchor. In a daylight-saving gap use the next valid local time; for overlaps use the earlier occurrence and store the resulting instant.
6. Imports preview using a normalized stable site/system key. Report missing values, ambiguous matches and duplicates by row. Capture content and mapping digest; applying that exact confirmed preview is idempotent. Commit a valid batch atomically; update only selected fields on existing records.

Verify expiry during replay, a worker crash after writing an object, two simultaneous submissions, a stale cached visit after reassignment and revocation of a public link. References: [Next.js data security](https://nextjs.org/docs/app/guides/data-security), [Supabase SSR clients](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

## M2a operation entry points

`/customers`, `/sites`, `/systems`, `/schedule` and `/visits/new` require owner/coordinator access. Register forms and scheduling share server-side validation/authorization and the transactional `save_operation` RPC. The workspace ID comes from verified server context; the RPC independently authorizes it. Stable per-form operation IDs protect repeated submissions. A successful form disables repeat input; refresh starts a new intended creation. Unknown-result retries must retain the original operation ID; durable offline retry storage follows in M4.

`operation_snapshot` serves the office register/schedule and the restricted field schedule. `/today` shows current-day assigned visits, their site-local window, site/address/access note, and planned system codes/rooms. Each visit opens its online field workspace.

## M2b online visit handover

`/visits/[visitId]` reads the restricted `visit_bundle` DTO. Assigned active technicians and active office staff can save findings; `/review` and `/preview` require owner/coordinator access. `visit_review_queue` lists submitted visits on `/office`. All calls use the caller's Supabase session and the active organization resolved by the DAL; each RPC independently checks verified identity and current access. The private staff-label bridge exposes only active staff email labels within an authorized visit, for choosing accountable owners and displaying attribution.

`visit_command(organization, visit, operation, kind, version, data)` implements `save`, `add`, `submit` and `return`. It locks organization then visit, checks current access before replay, binds actor-scoped operation receipts to the exact payload and rejects mismatched retries. Saves compare the item version, retain author/time and increment the aggregate version. Saves on separate items can succeed with their respective versions. The first saved finding starts the visit. Adding an existing same-site system is idempotent and marks it unplanned. Submission compares the aggregate version and atomically validates every item and active follow-up owner/deadline. Submitted visits reject field writes; office return requires a reason and retains correction history even after resubmission.

## M3a photo commands and delivery

`POST /api/field/attachments/prepare` reserves a stable attachment UUID with item, required caption/visibility, original file size/type and the verified caller as author. An equal retry reuses the reservation; changed metadata conflicts. `/upload` accepts bounded multipart data and signs the authenticated Cloudinary upload server-side with overwrite disabled. `/complete` independently reads provider metadata and submits a short-lived HMAC attestation to `attachment_command`; the database validates its actor/organization/object binding before marking the row verified. A direct Supabase call without that proof cannot mark an attachment verified. Upload responses and caller-provided URLs never establish verification.

Every endpoint authenticates the current session and active workspace; the RPCs independently enforce current visit access. Mutation routes require the configured application Origin. Inputs accept JPEG/PNG/WebP up to 8 MiB and verified dimensions up to 40 megapixels. Request bodies are bounded even without Content-Length. Only an editable visit can gain/lose evidence, and every evidence mutation increments its aggregate version. Pending reservations block submission until completed or explicitly removed. Captions/visibility are fixed for a reservation; remove and create a new reservation to change them.

`GET /api/field/attachments/[attachmentId]?visitId=...` serves verified images through an authenticated, private/no-store proxy. `customer=1` additionally denies internal images. Customer DTOs include only verified customer-visible attachment IDs/captions/dimensions, never provider URLs, signatures or private metadata. `/remove` tombstones an unsubmitted attachment before attempting provider deletion; it cannot be revived by a late upload/completion. Removed entries retain a retry-cleanup control if provider deletion fails. The protected provider object may remain until cleanup succeeds; automatic durable cleanup jobs are not implemented in M3a. A removed image is immediately unavailable to new app requests.

Drafts may retain a pending outcome or an incomplete follow-up. Submission blocks pending items, missing repair findings, missing follow-ups for repair/no-access and incomplete or revoked owners. No-access findings require a reason and cannot claim work, parts or measured values. The online pilot form supports temperature/current readings with context, explicit measurement states, decimal commas and multiple part lines. The customer preview/issuance mapping now lives in `hvac_private.customer_report_data` as described below. Photo verification is implemented in M3a; durable client drafts and replay/conflict resolution follow in M4.

## M3b issuance and revision entry points

The owner/coordinator's **Izdaj izveštaj** Server Action sends only visit ID, stable operation UUID and aggregate version to `issue_report`, using the active workspace resolved on the server. The RPC independently reauthorizes before replay and locks organization then visit, using the same order as membership/field/photo commands. It accepts no client-supplied snapshot, issuer, number, locale or job metadata. An atomic success returns the revision ID; the action revalidates office/visit views and redirects to `/office/reports/[revisionId]`.

`report_preview(organization, visit)` and issuance share the database allowlist. `report_revision(organization, revision)` serves frozen data plus current render state, and `report_list(organization)` serves the latest 20 issued records on the office home. Every read requires a verified active owner/coordinator. Assigned/unassigned technicians, other organizations and revoked members cannot issue or retrieve the office revision; raw revision mutation and private queue access remain denied. Permitted revision URLs survive sign-in destination validation.

The issue command requires a submitted visit, complete explicit findings and valid active action owners/deadlines, and rejects reserved or invalid verified uploads. All included customer evidence captures its Cloudinary identity/version and verified metadata. Simultaneous first issues, including different operation IDs, resolve to one revision and one `report-pdf:<revisionId>` job. A mismatched operation payload or stale unissued visit returns HTTP 409 (`PT409`); there is no transient serialization-error retry loop. Issued field/photo mutations are blocked. The office sees locked data and **PDF čeka izradu**, with no download/share action. Worker execution and archived bytes remain M3c, guest access M3d, and amendment M3f.

### M3c archive execution

The dedicated non-staff worker uses `pdf_claim`, `pdf_heartbeat`, `pdf_manifest`, `pdf_complete` and `pdf_fail` through the Supabase API. It persists expected SHA-256/size before `upsert:false` upload, reads back bytes for verification and completes only its live lease. A restart recovers an already uploaded object without replacing it. Missing-object rerenders must match the manifest; mismatches fail closed. Office retry is actor/operation-idempotent and requires current owner/coordinator access.

The web server never launches Chromium or uses SQL/service-role credentials. Staff `/api/office/reports/[revisionId]/pdf` reauthorizes the active workspace and ready artifact, downloads through the caller's Storage session, verifies digest/size and returns private/no-store bytes. No signed URL is exposed. Worker shutdown ends only its own Auth session, preserving other consumers' sessions.

### M3d guest report paths

Office Server Actions derive organization from the verified active workspace, validate the creation form, hash a server-generated 256-bit token and call `create_report_link`. The stable form token/operation make lost-response retries idempotent. Existing link status/revocation is available on the same revision page; raw links can be copied only when created. Default expiry is seven days; supported duration is 1–90 days. Links are delivered manually.

`GET /r/[token]`, `/r/[token]/pdf` and `/r/[token]/photos/[photoId]` use a fresh anonymous public-key client, independent of staff cookies. `guest_report` reauthorizes each request; invalid/expired/revoked links show a neutral unavailable page, while file endpoints return 404. PDF delivery uses the shared archived-byte verifier; photos use the shared frozen-reference image processor. File handlers recheck the capability after provider/Storage fetches. There are no signed download URLs or email side effects. M3e adds explicit receipt POSTs; GET requests have no acknowledgement side effect. Proxy response headers apply private/no-store, no-referrer and noindex to all guest routes, including failures. Production reverse-proxy/access logging must redact the full `/r/` path and the `x-report-token` header.

### M3e receipt POST

`POST /r/[token]/receipt` accepts JSON `{name, role, acknowledged: true}` up to 4 KiB. The web route requires the trusted `APP_URL` Origin, validates fields and calls `acknowledge_report` through a fresh anonymous client. Direct Supabase RPC calls independently validate capability, consent and fields; a staff session cannot substitute a guessed revision ID. Responses are private/no-store, no-referrer and noindex, with no raw input or capability in errors/logs.

The route returns the same recorded receipt on a matching retry (200), rejects different recorded details (409), unavailable capabilities (404), invalid input (422), excessive bodies (413) and unrelated origins (403). GET requests never acknowledge receipt. No additional message is sent or background render queued. The guest form preserves fields after an uncertain response for safe retry, and reload shows the persisted result. Office `report_receipts` remains authorized by active organization and role; a manual refresh fetches new results.

### M3f reviewed amendment

`report_amendment(organization, revision)` returns a safe complete operational replacement and active owner choices only to verified office staff for the latest revision. It excludes internal notes/private reading/material keys. `amend_report(organization, base_revision, operation, visit_version, reason, items)` independently validates access, complete coverage, versions and domain rules; callers cannot supply a ready-made customer snapshot, report number, issuer, identity or evidence. `amendmentSchema` reuses the field-entry schemas at the app boundary; SQL remains authoritative.

The correction form preserves edits through errors, previews the full customer document and submits a stable operation payload. Success redirects to the new immutable revision; history links and visit/preview reads resolve the highest committed revision. Creation, corrected operational values, append-only audit and the render job are atomic. Replays are authorized before return. Original field authors remain identifiable alongside the office correction actor/time. A v2 PDF is rendered by the existing lease/manifest pipeline, then shared/retried/revoked through the existing revision-scoped controls. Receipt and first-issue replay semantics do not follow the latest pointer.

### M3g follow-up commands

`follow_up_list` and `follow_up_command(organization, action, operation, version, kind, data)` require a verified active owner/coordinator. Commands lock organization, source visit and action, authorize before receipt replay, compare the action version and append a private before/after event. `assign` changes active staff owner and deadline; `complete` records an explicit internal completion note, actor and time. A captured `quote` is the quote-preparation task, not a quote approval.

`book` accepts site-local start/end and active assignees for an open repair/revisit action. It derives the source site/system and calls the existing M2 `save_operation` scheduler atomically. A unique action booking makes exact repeated proposals (even with new operation IDs) return one visit; different proposals conflict. Booking leaves deadline and open state unchanged. M5b owns subsequent schedule edits.

Once an office command manages an action, field saves and amendments may preserve its captured fields but cannot replace/delete it. Item/visit versions advance on office changes, without changing original field attribution. Completed actions retain their historical owner label after deactivation. `return_visit_source` authorizes the return visit and projects only its source system finding/work/access outcome/customer dependency; it grants no access to other source items, internal notes, photos or the entire original visit.

### M4a assigned download boundary

`GET /api/field/offline-context` verifies the current confirmed session and active workspace, returning `{identity, assignments, checkedAt}`. Identity contains the current user/organization IDs, account/organization labels and an opaque device epoch. `assignments` contains only that user's explicitly assigned visit IDs in the active organization; it is used to prune read-only local copies on successful reconnection. Responses are private/no-store and vary by Cookie. Known unauthenticated/unavailable membership returns 401; temporary service failures do not erase working copies. Inventory timestamps reject older overlapping replies.

`GET /api/field/visits/[visitId]` returns `{identity, bundle}` through `offline_visit_bundle`. Every caller, including an owner/coordinator, needs an explicit active assignment. The RPC independently checks verified identity, organization and assignment before reading the visit. Guessed, other-organization and unassigned IDs return a generic 404 from the web route; anonymous callers receive 401. No SQL/service-role credential participates.

Bundle schema 1 freezes download time and visit/item versions with the assigned field data. It excludes the unrelated available-system register, attachment delivery/provider credentials and arbitrary reading/material JSON metadata. The existing narrow return-source projection is included. Photo bytes and synchronization are excluded.

`teren_offline_epoch` is a readable random invalidation nonce, not a session token or authorization credential. Actual Auth/workspace cookies remain HTTP-only. Sign-in/up, sign-out, password changes, verified callbacks and workspace selection rotate the epoch. The client accepts an identity binding only from the authenticated context response matching the current epoch and local boundary marker. Old in-flight responses and an old tab cannot activate another identity's partition. Browser partitioning never substitutes for current server authorization.

### M4b local queue boundary

M4b adds no server write endpoint. Device drafts capture the current actor, downloaded base versions and one stable operation ID; validated queued payloads are still unsent. Online save/submit controls are paused when the same browser has pending drafts. M4c now sends through current authenticated/assigned M2b commands, persists an attempt before transport, acknowledges each operation only after server confirmation and never replaces an attempted payload under its existing ID. Device attribution is provenance, not authorization. See [FRONTEND.md](FRONTEND.md) for storage/identity rules.

### M4c replay endpoint

`POST /api/field/sync` requires the configured application Origin, verified session and active workspace. A maximum 200,000-byte JSON body contains `{userId, organizationId, epoch, operations}`; these identity fields must match the verified context. At most ten ordered operations are accepted. Each operation is `{operationId, entityId, baseVersion, type, payload}` where `entityId` is the visit UUID, `type` is `save` or `submit`, and the payload reuses the online item schema or an empty submit object. Actor identity is derived from the caller's session, never a draft label. Add/return/evidence commands are outside this slice.

Each operation calls `replay_field_command` in its own database transaction through the caller's Supabase session. The wrapper locks organization then visit, checks live membership and explicit assignment (including office callers) before replay, and delegates writes to `visit_command`. Private actor-scoped replay receipts preserve the exact original acknowledgement: item values/version, aggregate version/state, attribution and confirmation time. Matching retries return that result even after a later submission; changed payloads conflict. No SQL/service-role credentials are used at runtime.

The response is `{results: [{operationId, status, acknowledgement?, error?}]}`. Each acknowledgement identifies operation, visit, type and base version, and contains the safe saved item (for save), minimal visit lifecycle fields and confirmation time. Per-operation 404/409/422/503 failures are sanitized. Later operations receive 424 after the first failure; earlier transactions remain committed. Envelope errors return 401/403/409/413/422. All responses are private/no-store. The client sends submission only after all prerequisites are acknowledged; SQL independently validates aggregate versions, every item/action and pending attachments. A changed aggregate requires explicit recovery, not blind rebasing.

### M4d offline photo transport

`POST /api/field/offline-photos/{prepare,upload,complete,remove}` uses the existing M3a `attachment_command`, signed authenticated Cloudinary uploader, independent provider verification and server HMAC. JSON requests are bounded to 10,000 bytes and carry the reservation metadata plus `device: {userId, organizationId, epoch}`. Upload uses multipart `metadata` JSON and `file`, bounded to 8 MiB + 64 KiB. The configured application Origin, current verified session, selected workspace, device binding and explicit assignment are required before provider access. The captured author must match the caller. An office role alone does not grant offline-photo access.

`prepare`, `complete` and `remove` call `replay_photo_command` through the caller's session. The private actor/attachment/phase receipt stores the original acknowledgement and canonical logical payload. Completion excludes expiring proof fields from replay equality while still requiring a fresh valid attestation for the initial mutation. Receipts return cumulative per-phase visit-version effects so a lost/out-of-order acknowledgement can be applied exactly once. Current assignment is checked before receipt replay; domain transitions and image validation remain in M3a.

Before uploading again, the client probes completion. A missing provider image returns 404 `photo_not_uploaded` and permits upload; an unsupported actual format/dimension returns 422 `invalid_photo`, retaining the Blob for correction/removal. Upload failures and service interruptions return 503; identity conflicts return 409, inaccessible records return 404 and expired sessions return 401. Provider URLs, credentials, original error details and verification proofs never reach the client. Each attempt signs/attests afresh; there is no persisted browser upload permission to reuse after expiry. Responses are private/no-store and excluded from the service worker.

Removal persists an inaccessible tombstone and a stable receipt before provider cleanup. If the reservation result was unknown, the wrapper atomically reserves/removes the same ID so a delayed preparation cannot create a new live attachment. Cumulative effects include those own changes; queued submission does not blindly adopt unrelated aggregate versions. A failed provider deletion returns `cleanupPending` without reviving evidence. The original online M3a endpoints remain compatible. Server attachment reservations independently block submission even if a client bypasses the local queue.

### M4e recovery snapshot and reviewed replacement

`POST /api/field/recovery` is a bounded private/no-store read (50,000-byte JSON) requiring the configured Origin and verified `{userId, organizationId, epoch}` binding. It accepts a visit ID, one optional original save/submit envelope and up to 100 local photo IDs. `field_recovery_context` locks organization then visit and requires current explicit assignment before reading the safe bundle, evidence captions/visibility/state, the caller's matching command acknowledgement and caller-owned photo phase receipts. A matching committed operation is acknowledged rather than replaced. Missing/mismatched receipts do not authorize overwriting current values. Anonymous, another tenant and unassigned/revoked users receive no snapshot.

A reviewed sync operation may include `reconcileFrom`, a different previous operation UUID. The sync route then invokes `reconcile_field_command`, preserving the ordinary item/submit schemas and expected versions. This RPC reauthorizes, rejects reuse of a committed predecessor, performs the normal replay/visit command and atomically writes a private reconciliation audit with actor, predecessor/new IDs, exact replacement payload and safe server-before snapshot. Equal retries return the original acknowledgement; changed predecessors/payloads conflict. A new server change after review still returns PT409. Finalized visits and office-managed actions retain their existing protection.

The device atomically archives superseded work and stages the reviewed replacement. Choosing server values is a local adoption, not a server save. Session renewal and assignment restoration keep attempted payloads frozen until acknowledged; they never transfer an operation to a different actor or organization. Conflict status pauses photo upload for that visit. Existing provider and database assignment checks independently deny withdrawn uploads/replays even when an old device copy remains.


### M4f transition boundary

Lifecycle decisions are device-only and add no server endpoint or migration. Sync-before-transition reuses the authenticated M4c/M4d replay and checks durable pending records again before continuing. Keep invalidates the current browser binding before the existing auth/workspace server action; server epoch rotation and every replay's live authorization remain authoritative. Explicit cleanup never changes server receipts/evidence/history. Attempted pending operations and provider cleanup intents cannot be discarded locally until settled, preserving retry IDs after uncertain responses. See [FRONTEND.md](FRONTEND.md) for scope, unsaved-input and shared-device behavior.


### M5a register commands and authorized history

`register_command(organization, entity, operation, kind, version, data)` accepts customer/site/system `update`, `archive` and `restore`, plus unit `create`, `update`, `replace` and `archive`. Kinds use `entity.action`. Unit creation targets the system; replacement/update/archive target the component. Replacement IDs and new-component IDs equal the stable operation UUID. Caller identity comes from verified Auth, never form fields. Payloads are bounded objects; UUIDs, versions, required fields, time zone, field lengths, component role and active ancestors are validated independently in PostgreSQL. Parent IDs cannot be changed. A private audit/receipt stores the original row and exact command/result. SQL authorization precedes replay. See [DATABASE.md](DATABASE.md).

Owner/coordinator Server Actions at register detail routes retain form values on validation/stale errors and require explicit UI confirmation for archive/replacement. They always use the active workspace and caller-scoped Supabase client, then invalidate affected register/schedule/field views. No privileged runtime SQL or new environment variable is used.

`register_detail(organization, kind, entity)` returns a server-owned detail DTO. Office staff can follow the customer → site → system hierarchy; technicians can open only an assigned system. History is read-only, limited to submitted/issued findings for the authorized scope and projected through the report reading/material allowlists. The existing field bundle now includes stable `systemId` links and omits archived add-on systems. Its contact prefers site contact, falling back to customer contact. Unissued previews and first-issue snapshots inherit that mapping; old frozen revisions remain unchanged. Offline downloads retain the system ID, but the complete history page requires connectivity; no new private response is service-worker cached.
